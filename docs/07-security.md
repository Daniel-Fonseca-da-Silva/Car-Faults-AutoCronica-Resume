# 07 · Security and privacy

[← Back to README](../README.md)

A summary of the platform's defenses, organized by threat. Each row points to where the defense is implemented.

## Threat model (summary)

| Threat | Impact | Main defense |
|---|---|---|
| Bots firing new lookups to burn AI quota | Cost, exhausting free-tier providers | Turnstile (web) + per-IP quota (mobile), **only on the AI path** |
| Session theft via XSS | Account takeover | JWT in an `httpOnly` cookie; the browser never reads it (BFF) |
| Reusing a token after logout | Unauthorized access | `jti` denylist in Redis until `exp` |
| Privilege escalation to admin | Tampering with the catalog | `AdminGuard` in the API on every `/admin` route; the web only hides the UI |
| Prompt injection through vehicle fields | Manipulated output, prompt leakage | Input regex/limits, delimiters, prompt rules, output validation |
| Hallucinated sources/URLs | Misinformation | URL filter + restriction to RAG sources |
| Malicious uploads | Arbitrary content stored | MIME type and size checks, server-generated key, R2 URL required |
| Community abuse | Spam, harassment | Reports + moderation queue |
| Fake AI in production | Invented content | Stub forbidden in production in both services |

## Authentication

- **Google OAuth2** is the only sign-in method. No passwords are stored.
- **JWT** signed with `JWT_SECRET`, carrying `sub` (user id) and `jti` (a random UUID per issuance). Accepted either as the `access_token` cookie or as `Authorization: Bearer`.
- On every authenticated request, `JwtStrategy.validate`:
  1. rejects the token if its `jti` is in `jwt:deny:{jti}`;
  2. loads the user (cached) and rejects the token if the user no longer exists.
- **Web**: the OAuth redirect only carries a **single-use code** (32 random bytes, 60 s, deleted when read), never the JWT. The web exchanges it on the server and stores the JWT in an `httpOnly; SameSite=Lax; Secure` cookie on its own domain.
- **Mobile**: the Google `idToken` is verified with `google-auth-library` against the web and Android client IDs. The JWT lives in the Keystore/Keychain via `flutter_secure_storage`.
- **Logout** revokes the token on the server and then clears the client.

## Authorization

| Level | Mechanism |
|---|---|
| Public | No guard |
| Optional session | `OptionalJwtAuthGuard`: personalizes (e.g. `myVote`, search logging) without requiring login |
| User | `JwtAuthGuard` + ownership checks in the service (only the author can edit/delete reviews, comments and fixes) |
| Admin | `JwtAuthGuard` + `AdminGuard` (`role === 'admin'`) on every `/admin/*` controller and on vehicle-image upload |

The web applies UX guards (`proxy.ts` middleware + `requireAdminUser()`), but **the API is always the authority**.

## Protecting the AI and traffic

| Layer | Configuration |
|---|---|
| Global throttler (Nest) | `THROTTLE_TTL_MS` / `THROTTLE_LIMIT`, per IP |
| Auth throttler | `THROTTLE_AUTH_*` on `/v1/auth/*` |
| Lookup throttler | `THROTTLE_LOOKUPS_*` on `/v1/lookups/*` |
| Turnstile | Required for web clients **only** when the lookup will generate/translate with AI; `TURNSTILE_ENABLED=false` only locally/in tests |
| Mobile AI quota | `throttle:ai:mobile:{ip}` with `THROTTLE_AI_MOBILE_*` |
| AI service | Bearer `API_KEY` (constant-time comparison with `secrets.compare_digest`), slowapi `RATE_LIMIT` per IP, body ≤ 256 KiB, CORS off by default |
| Retries | Nest: 1 retry for fast failures only; AI: 2 retries per provider with backoff. Avoids amplifying spikes |

## Input and output validation

- **Nest API**: `ValidationPipe` with `whitelist` + `forbidNonWhitelisted` (unknown properties → `400`), `class-validator` on every DTO (e.g. year ≥ 1900, doors 1-6, `details` ≤ 1000).
- **Responses** always go through `*ResponseDto`; no entity is serialized directly.
- **AI service**: vehicle fields limited to the regex `^[A-Za-zÀ-ÖØ-öø-ÿ0-9 .\-/()+]+$` and 64 characters. LLM output is schema-validated, normalized, **may not contain `<`/`>`**, has size limits, and sources are filtered (`https` only, valid domain, no IPs; with RAG, only chunk URLs).
- **Defensive parsing in Nest** (`parseAiLookupResult`) before the AI response is saved.

## Uploads (Cloudflare R2)

- `multipart/form-data`, only `image/jpeg`, `image/png` and `image/webp`, max 5 MB (`ParseFilePipe` + `MaxFileSizeValidator`).
- The object key is generated by the server: `comments/{userId}/{uuid}.{ext}` or `vehicles/{uuid}.{ext}`. The client can't choose paths.
- `comments.image_url` must start with `R2_PUBLIC_BASE_URL` (`IsR2ImageUrl`), so it can't point at external domains.
- Catalog images: admins only.

## Headers, CORS and cookies

- `helmet()` on the API (CSP off, since the API serves no HTML).
- API CORS: explicit list in `CORS_ORIGINS`, `credentials: true`, no wildcard.
- API cookie: `COOKIE_SAME_SITE` (default `lax`) and `COOKIE_SECURE` (must be `true` with `none`).
- The web uses its own `SameSite=Lax` cookie, so it doesn't rely on third-party cookies.

## Secrets and configuration

- Every secret comes from environment variables. `.env`, `env/dev.json`, `env/prod.json` and `android/key.properties` are gitignored, and each repository has a `.env.example` with no values.
- **No secrets, credentials or production infrastructure identifiers are included in this documentation.** Variable names are documented; values are not.
- The secrets shared between services are few and explicit: `API_KEY` (AI) = `AI_API_KEY` (Nest); `GOOGLE_CLIENT_ID` (Nest) = `GOOGLE_SERVER_CLIENT_ID` (app); `R2_PUBLIC_BASE_URL` (Nest) = `NEXT_PUBLIC_R2_PUBLIC_BASE_URL` (web).
- `TURNSTILE_SECRET_KEY` only exists in the API; the web only knows the public sitekey.
- **Fail-safe in production**:
  - Nest refuses to start with `AI_PROVIDER` ≠ `http` when `NODE_ENV=production`.
  - The AI service refuses to serve with the stub, or with no provider key at all, when `APP_ENV=production`.
  - The AI service turns off `/docs`, `/redoc` and `/openapi.json` in production.

## Runtime images

Both backends run on **distroless nonroot** images (`gcr.io/distroless/nodejs24-debian13` and `python3-debian12`): no shell, no package manager, no root user. Builds are multi-stage, and dev dependencies never reach the final image. The AI service's CI runs `pip-audit` on its dependencies.

## Privacy and GDPR

| Topic | Implementation |
|---|---|
| Data collected | Name, email and avatar from the Google account; published content; activity (searches, issues viewed, favorites) for the user's own stats |
| Policy | `/privacy` on the web (3 languages) and a legal screen in the app (`assets/legal/privacy_*.json`) |
| Account deletion | App (Profile → danger zone), web (Profile), and the public `/account-deletion` page. The API anonymizes and soft-deletes |
| Web cookies | Accept/Reject banner; Google Consent Mode starts as `denied`; AdSense and Vercel Analytics only after accepting |
| In-app ads | UMP consent before AdMob is initialized; no consent, no ads |
| Avatars | The Google profile picture URL; there's no avatar upload |
| Screenshots in these docs | They show the maintainer's own account and content (name on a comment); no internal IDs or other users' data |

## Known limits and next steps

- The mobile quota is per IP: users behind the same NAT (e.g. a mobile carrier) share it. A future option is the Play Integrity API.
- `X-Client: mobile` is self-declared. Any client can send it to swap Turnstile for the per-IP quota; the limit still applies.
- The `admin` role is assigned directly in the database; admin actions are not audited.
- The AI service's rate limit is in memory unless `REDIS_URL` is set. With several instances it should use Redis.
